# Implementation plan — Marketplace and Franchise

This is the deliverable §40 of the Master Architecture Specification asks for
before any large change: an assessment of what exists, what has to be built,
what breaks, and in what order. It is written against the spec's own headings
A–Q.

Nothing in this document has been built yet. §40 says to wait for approval
first, and the reasons to wait are real — one of the changes below moves the
column the whole storefront currently prices itself from.

---

## The size of this, said plainly

The spec describes a platform with roughly a dozen domains. The codebase has
one and a half of them, and they are good ones, but the distance is not small:
this is a quarter's work for a team, not an afternoon's. Anything that claims
otherwise will produce something that looks like a marketplace and cannot take
money safely.

What that means practically: it gets built in phases, each one shippable, each
one leaving the site working. §Q is that order.

---

## A. Current architecture assessment

**Laravel 13.23 on PostgreSQL 16.** A flat, conventional Laravel layout — no
domain modules yet, and per §25 that is fine while the code is this small.

**What is solid.** The catalogue core, and it is solid in exactly the way the
spec asks for:

| | |
|---|---|
| `products` | one shoe model — §4 and §13's canonical Product |
| `variants` | colour × size, own SKU, integer Rial, `sellable_stock` generated by the database |
| `variant_media` | gallery bound to a colourway, not to a size |
| `categories`, `brands` | with a nav-visibility decision stored, not guessed |
| `inventory_movements` | an append-only stock ledger |

The invariants are CHECK constraints in the database, not checks in PHP: stock
never negative, a reservation never above what is on hand, a sale price never
above the struck-through one, a promotion window ordered. §30 and §31 ask for
exactly this and it is already true.

**The storefront.** One route. The home page, rendering from the catalogue,
pixel-identical to the design preview at four widths (`node theme/check-parity.js`).

**What does not exist.** Authentication beyond a `User` model; customer
accounts; cart; checkout; orders; payments; shipping; promotions; search;
any admin surface; vendors; commissions; settlements; branches; tenancy;
roles and permissions.

So: §2's storefront is one page of perhaps fifteen, and §3 and §10 — the two
halves of the spec — are not started.

## B. Existing components that can be reused

Reused as they are, not rewritten:

- **The canonical catalogue.** `Product` + `Variant` + `VariantMedia` is
  already the "canonical product" §13 and §27 insist on. Vendors and branches
  attach offers to it; nothing about the product record duplicates.
- **`inventory_movements`.** The ledger shape §7 wants for vendor finance is
  the shape this already is for stock. The same discipline extends.
- **The database-level invariants.** They carry into per-branch inventory
  unchanged.
- **The storefront views.** §12 requires one shared storefront for every
  branch. The views must become tenant-aware; they must not be copied.
- **`config/storefront.php` and `page_url()`.** The per-site configuration and
  the link map become per-tenant settings under §28 with little change in
  shape.
- **`theme/check-parity.js`.** Whatever happens to the data layer, this still
  says the page did not move.

## C. Required new Marketplace components

```
vendors                vendor identity, status, approval state
vendor_users           staff accounts, role per vendor
vendor_offers          vendor_id + variant_id -> price, stock, status, SKU
commission_rules       global / vendor / category / product, percent or fixed
ledger_entries         sale, commission, refund, adjustment, settlement,
                       charge, bonus, reversal  (§7 — append only)
settlements            request, state machine, reference, admin notes
settlement_items       which ledger entries a settlement discharges
```

Plus: vendor dashboard, vendor product submission with admin approval (§4),
vendor fulfilment ownership on the order item (§9).

## D. Required new Franchise components

```
branches               a store: central, or a franchise branch
branch_domains         host -> branch, so custom domains are data (§34)
branch_users           staff accounts, role per branch
branch_offers          branch_id + variant_id -> price, discount, is_active
branch_inventory       branch_id + variant_id -> on hand, reserved
branch_settings        address, hours, contact, banners, feature flags (§28)
price_policies         central-only / branch-may-set / min / max / max discount
```

Plus: tenant resolution middleware, a tenant context available for the whole
request, the franchise admin panel, and the isolation tests §18 requires.

## E. Database schema changes

**The one that matters, and the reason this document exists before any code:**

> `variants.price`, `variants.compare_at_price`, `variants.stock_on_hand`,
> `variants.stock_reserved` and the generated `variants.sellable_stock` have
> to leave the variant.

Under §13, §14 and §16 a price and a stock level belong to a *seller in a
place*, not to the shoe. The same Jordan 1 size 38 is 3,150,000 with 4 left in
Shiraz and 3,090,000 with 7 left in Tabriz. A variant cannot hold that.

After the change a variant is identity only — product, colour, size, SKU,
weight — and commerce moves to:

```
branch_offers     (branch_id, variant_id) -> price, compare_at_price, active
branch_inventory  (branch_id, variant_id) -> on_hand, reserved, sellable
vendor_offers     (vendor_id, variant_id) -> price, stock, status
```

This is the change that breaks things. Everything that prices the storefront
today reads `variant->price`.

**Recommendation, and it needs a decision.** Model the main store as the
**central branch** — a row in `branches` with `type = 'central'` — rather than
inventing a third pricing mechanism for it. §16's own diagram shows a Central
Warehouse standing alongside Shiraz, Tehran and Mashhad, and one uniform
offer/inventory mechanism is far less to get wrong than two. Franchise
governance rules (§15's price policies, §19's panel) apply only to rows with
`type = 'franchise'`, so §37's "never treat them as identical" stays honoured
where it is about business rules. Vendors stay entirely separate, as §1
demands.

**Other schema work:** roles and permissions with tenant scoping (§24);
`customers` separated from staff `users` (§21); carts scoped to a store (§22);
orders and order items with frozen commercial data (§23); `audits` (§29);
`stock_reservations` with expiry (§31).

## G. Tenant resolution strategy

Subdomain first, but resolved through data so custom domains cost nothing
later (§34):

1. Middleware reads the request host.
2. Looks it up in `branch_domains`. Apex `vikyplus.ir` resolves to the central
   branch; an unknown host is a 404, never a silent fallback.
3. Binds a `TenantContext` singleton for the request — the branch, its
   settings, its feature flags.
4. Global query scopes on every branch-scoped model read that context, so a
   query that forgets the tenant returns nothing rather than everything.

Storefront routes get the tenant middleware. Admin routes resolve the tenant
from the authenticated staff user's branch instead, never from the URL.

## H. Commission and settlement architecture

Resolution order, most specific first: **product → category → vendor →
global**. Percentage or fixed, with room for hybrid (§6).

The rate is resolved **once, server-side, at the moment the order is placed**,
and written onto the order item along with the price. §23 is explicit that
history must not be reconstructible from current tables, and a commission rate
changed next month must not rewrite last month's revenue.

Every movement writes an append-only `ledger_entries` row. A vendor's payable
balance is **derived by summing the ledger**, never stored as an editable
number (§7). Settlements select ledger entries, move through
pending → approved → processing → paid, and can be rejected or cancelled (§8).

## I. Inventory architecture

Stock lives per (branch, variant) and per (vendor, variant) — §14's
size-by-size table, in a table.

Against overselling (§31): reserve inside a database transaction with `SELECT
… FOR UPDATE` on the inventory row, write a `stock_reservations` row with an
expiry, and let payment success convert the reservation to a sale, payment
failure or expiry release it. The CHECK constraints stay as the last line of
defence: even a bug cannot drive stock negative, because the database refuses.

`inventory_movements` keeps explaining every change, per branch.

## J. Cart and order changes

Cart is scoped to (customer or session) **× store context** (§22). Entering
Shiraz means a Shiraz cart at Shiraz prices; it must not mix branches, and
marketplace multi-vendor carts are a different thing and stay different.

At checkout every commercial number is recomputed server-side from the
database and **frozen** onto the order item: unit price, discount, tax,
commission, seller payable, fulfilment owner, refund state (§5, §23). Nothing
priced by the browser is trusted (§30).

Vendor ownership is on the **order item**, never only on the order (§5).

## K. Authentication and authorization changes

One customer identity across the whole ecosystem (§21): an account made on
`vikyplus.ir` works on `shiraz.vikyplus.ir`, while carts, orders and prices
stay per store. That argues for splitting `customers` from staff `users`.

Staff authorization is Role + Permission + Resource ownership + Active tenant
(§24). A Shiraz manager's policy check fails on a Tehran order not because the
UI hides it but because the policy and the query scope both say no (§18).

## L. Admin panel changes

Three surfaces, one codebase: central admin (§20), franchise panel (§19),
vendor dashboard (§3). **This needs a decision** — building three admin UIs by
hand is a large fraction of the total effort, and an admin framework
(Filament) would cut it substantially at the cost of a significant dependency.
Worth deciding before, not during.

## M. Required routes and APIs

Storefront (tenant-scoped): home, category, product, search, cart, checkout,
account, orders, wishlist. Vendor: dashboard, products, offers, orders,
finance, settlements. Franchise: dashboard, inventory, pricing, orders,
settings, staff. Central: franchises, vendors, catalogue, commissions,
settlements, reports. Every non-storefront route behind auth plus a policy.

## N. Security considerations

Beyond §30's list, two things already true in this codebase that must change
before untrusted input reaches them:

- **Mass assignment.** Every model is `protected $guarded = []`. That is
  harmless while a seeder is the only writer and dangerous the moment a vendor
  form posts to one. Each model needs a real `$fillable` before it is
  writable from a request.
- **No authorization layer exists yet.** There is nothing to bypass today, but
  policies must land in the same phase as the first non-public route, not
  after it.

And the rule that governs all of it: never trust `price`, `commission`,
`branch_id`, `vendor_id` or payable amounts from the frontend.

## O. Migration risks

1. **Moving price and stock off `variants` is the destructive one.** The
   storefront, `CatalogueSeeder`, `HomeController` and the home page's Blade
   all read those columns today. Plan: add the new tables, backfill from the
   variant columns, move the readers, verify the page has not moved with
   `check-parity.js`, and only then drop the old columns. Never in one step.
2. **`sellable_stock` is a generated column.** It cannot simply be moved; the
   generated expression has to be recreated on the new table.
3. **Tenant scoping is retroactive.** Every existing query becomes wrong the
   day a second branch exists. The global scopes must land with the branches
   table, not later.
4. **The zero-pixel guarantee.** The home page currently matches the design
   preview exactly. Every phase below must end with `check-parity.js` still
   reporting zero, or with a deliberate, recorded decision that it should not.

## P. Testing strategy

- **Tenant isolation is not optional** (§18): a test per branch-scoped
  resource proving a Shiraz staff account cannot read or write a Tehran row by
  id, by URL, or by direct request.
- **Concurrency**: two simultaneous purchases of the last unit; one wins.
- **Money**: commission resolution order; frozen order data unchanged by later
  price edits; integer Rial arithmetic exact.
- **The storefront**: the existing feature tests, plus `check-parity.js` in CI.

## Q. Step-by-step implementation phases

Each phase leaves the site working and is worth shipping on its own.

| Phase | What | Why here |
|---|---|---|
| **0** | Roles and permissions; `customers` split from staff `users`; `audits`; `$fillable` on every model | Everything after this needs an actor and an audit trail |
| **1** | Branches, `branch_domains`, tenant resolution, `TenantContext`, global scopes, isolation tests | The riskiest structural change; earlier is cheaper |
| **2** | Move price and stock to `branch_offers` and `branch_inventory`, central branch backfill, storefront reads the tenant's offer | The destructive migration, done once, behind the parity check |
| **3** | Catalogue browsing: category pages, product pages, search, filters — all tenant-scoped | The storefront becomes a shop |
| **4** | Cart, reservations, checkout, payment, orders — with the overselling defence | The site can take money |
| **5** | Franchise admin panel; price policies; branch settings and feature flags | Branches become self-managing |
| **6** | Marketplace: vendors, offers, approval, vendor dashboard | The second business line opens |
| **7** | Commission, ledger, settlements, reporting | Marketplace money becomes auditable |

Phases 0–2 are foundation and should not be split across long gaps: between
phase 1 and phase 2 the schema is in a half-moved state.

---

## Decisions taken

The three §40 questions have been answered by the client:

1. **The main store is the central branch.** One row in `branches` with
   `type = 'central'`, one pricing and inventory mechanism for everything.
   Franchise governance — §15's price policies, §19's panel — applies only to
   rows with `type = 'franchise'`. Vendors stay a separate domain entirely.
2. **The admin surfaces are hand-built**, in the same design language as the
   storefront, rather than on Filament. This makes phases 5–7 substantially
   larger and that is accepted; the panels will look like the shop rather than
   like an admin framework.
3. **Phase 0 first, then 1 and 2 without a gap**, since the schema is
   half-moved between 1 and 2.

## Progress

- **Phase 0 — foundation.** Roles and permissions, customers separated from
  staff users, an audit trail, and a real `$fillable` on every model.
  *Done.*
- Phases 1–7: not started.
