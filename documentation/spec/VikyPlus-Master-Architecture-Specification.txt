5. MULTI-VENDOR ORDERS
A customer must be able to purchase products from multiple vendors.

IMPORTANT: Vendor ownership must exist at ORDER ITEM level.

Do NOT rely only on vendor_id at the order level.

  Order
  |
  +-- Order Item -> Vendor A
  +-- Order Item -> Vendor A
  +-- Order Item -> Vendor B

Each order item must retain enough commercial information to reconstruct the transaction later:

  seller/vendor

  variant
  quantity
  unit price
  discount

  commission

  fulfillment status
  refund status

Historical order data must not break if the current product price changes later.


6. MARKETPLACE COMMISSION SYSTEM
The platform earns commission from marketplace transactions. Commission architecture should
support:

  Global default commission
  Vendor-specific commission
  Category-specific commission
  Product-specific commission if required
  Percentage commission
  Fixed commission if required
  Future extensibility for hybrid commission rules

  Example:
  Product Sale: 3,000,000
  Platform Commission: 15%
  Platform Revenue: 450,000
  Vendor Payable: 2,550,000

Commission calculations must be recorded as financial transaction data and remain auditable.

9. MARKETPLACE FULFILLMENT
Marketplace fulfillment must be designed separately from Franchise fulfillment.

  Vendors ship orders themselves
  Platform fulfillment
  Mixed fulfillment models

Each Order Item should retain fulfillment ownership. Returns, cancellations and refunds must work
correctly in multi-vendor orders.


10. FRANCHISE / BRANCH NETWORK
Implement a separate Franchise domain. Franchises are official stores/branches of our brand.

  Physical
  Online
  Physical + Online

Every franchise should receive a FULL version of our main e-commerce storefront.

  Do NOT create a simplified Mini Store.
  Do NOT create separate Laravel applications.
  Do NOT duplicate the storefront codebase.

There must be ONE Laravel Core, ONE shared storefront, and MULTIPLE franchise tenants.

18. TENANT ISOLATION
This is CRITICAL.

Franchise data isolation must exist at backend level. A Shiraz franchise administrator must NEVER
access Tehran data by changing URLs, API IDs, manual API requests, frontend requests, or guessed
identifiers.

Tenant isolation should be enforced through:

  Middleware
  Policies
  Query scopes
  Service-layer validation
  Repository rules if repositories are used
  Authorization
  Automated tests

Do NOT rely only on frontend restrictions.

22. CART ARCHITECTURE
Cart must be Store/Branch scoped.

Do NOT accidentally allow one cart to mix Shiraz franchise inventory with Tehran franchise
inventory unless cross-branch ordering is explicitly introduced later.

Recommended behavior:

  Customer enters Shiraz store.
  Cart belongs to Shiraz.
  Products use Shiraz price, stock, discount and availability.
  Checkout creates an order associated with Shiraz.
  Store branch_id/store_id on the order.

Marketplace multi-vendor carts are a separate concept and must not be confused with Franchise
cross-branch carts.


23. ORDER ARCHITECTURE

  Shipping method
  Payment
  Fulfillment ownership
  Commission where Marketplace applies
  Refund information

30. SECURITY
Pay particular attention to:

  Tenant isolation
  Vendor isolation
  Authorization
  IDOR prevention
  Price manipulation
  Cart manipulation
  Inventory race conditions
  Overselling
  Payment verification
  Settlement integrity
  Admin actions
  Mass assignment
  API authorization
  File uploads
  Rate limiting where appropriate

Never trust price, commission, branch_id, vendor_id or payable amounts sent from the frontend.
Commercial calculations must be performed and verified server-side.

  Manual inventory adjustment

37. IMPORTANT BUSINESS DISTINCTION
Never treat MAIN STORE, MARKETPLACE VENDOR and FRANCHISE BRANCH as identical
concepts.

They may share Products, Customers, Payments and Infrastructure, but their business rules are
different.

  Marketplace:
  Independent seller
  Platform commission
  Vendor payable
  Vendor settlement


  Franchise:
  Official brand branch
  Branch-specific inventory
  Branch-specific pricing
  Branch-specific storefront
  Central franchise governance


  Main Store:
  Brand's central direct sales operation

39. IMPLEMENTATION APPROACH
  Inspect the existing Laravel project.
  Understand the current Authentication, Product model, Product variants, Inventory, Cart,
   Orders, Payments, Admin panel, Frontend architecture, Routes, APIs and Database schema.
  Identify reusable components.
  Do NOT unnecessarily rewrite working functionality.
  Design Marketplace and Franchise domains around the existing stable core where technically
   reasonable.
  Identify schema changes.
  Identify required migrations.
  Identify security risks.
  Identify potential breaking changes.
  Create an implementation plan.
